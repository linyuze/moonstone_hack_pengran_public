# 架构（应用端）

```
浏览器
  │  静态资源（构建产物，无源码）
  ▼
数字孪生服务 (Python, 127.0.0.1:5186)
  ├─ GET  /                  → Web 构建产物
  ├─ GET  /twin/             → Three.js 三维厨房
  ├─ POST /api/recipe        → 菜单编译成动作序列，启动仿真会话
  ├─ GET  /api/recipe        → 会话快照（温度曲线、关节角、步骤、出餐）
  ├─ POST /api/simulation    → 调速 / 停止 / 手动动作
  └─ *    /api/menu/*        → 反向代理到 Web API
                                │
                                ▼
                        Web API (Node, 127.0.0.1:5186+1000)
                          └─ 模型调用、菜单结构校验、料筒能力闸门
```

单端口对外，两个进程，无 Docker、无 MQTT broker。

## 一次烹饪的数据流

1. **菜单**：`POST /api/menu/generate` 携带库存、人数、口味、忌口、采购模式。
   服务端拼提示词 → 调模型 → `validateMenuOutput` 做结构、克数、忌口、辣度校验。
2. **料筒闸门**：菜单里出现本机 19 个食材筒 / 15 个调料筒之外的名称时，
   该候选被判 `blocked`，触发一次按真实料筒重写的重试；仍不可执行才给出
   标注清楚的替代方案。
3. **编译**：`POST /api/recipe` 把已核对菜单按语义词表映射到具体槽位，
   生成 `dispense / water / layers / lid / cook / serve / clean` 动作序列。
   未知食材、缺失用量、不支持做法、忌口冲突、整餐库存不足都在**运动之前**拒绝。
4. **执行**：服务端时钟推进热模型（接触传热 + 蒸发）、PID、六轴机构与重力，
   每一步都有 accepted / completed 事件；`speed=8` 同时作用于全部子系统。
5. **出餐**：统计转移质量，保留食材种类与外观，随后冷却与自清洁。

## 与真机的边界

- 仿真会话是完整闭环，可以直接演示。
- 真实机械臂（Panthera-HT / AIRBOT）只提供**只读**反馈通道；
  `/api/arm/execute` 在未完成现场标定前固定返回 409。
- 温控曲线与传热系数未经实物标定，不能据此判定食品熟度；
  出餐品相保持 `unverified`。
